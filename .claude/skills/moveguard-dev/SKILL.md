# MoveGuard 개발 스킬

MoveGuard는 K-디지털 트레이닝 해커톤(팀 아이디업) 출품작으로, 스마트폰 영상에서 관절 좌표를 뽑아 RULA(추후 REBA·OWAS) 기준으로 근골격계 위험도를 자동 채점하고, KOSHA 법정서식(유해요인조사표) 초안을 자동 생성하는 서비스다. 이 스킬은 매번 처음부터 프로젝트를 설명하지 않아도 되도록, 지금까지 확인된 사실과 지켜야 할 원칙을 정리해둔 것이다.

## 0단계 — 항상 먼저 확인할 원본 자료

작업 전에 아래 문서들이 "사실의 근거"다. 추측하지 말고 이 파일들을 직접 열어서 확인한다.

- **팀이 이미 제출해서 통과한 기획서** (모든 기능·기술스택·검증방법의 공식 약속): `예선진출용 제출서류_최종/최종제출본/2. 개발기획서_아이디업.pdf`
- **RULA 정밀 스펙(Table A/B/C 조견표, 근골격계부담작업 11가지, 법정서식 매핑)**: `팀공유자료/1. MoveGuard_MVP_팀공유자료_v4_20260724.pdf`
- **KOSHA 공식 서식 원본**: `서식모음/`, `가이드라인모음/`
- **대회 규정(본선 진행방식, 심사기준, 일정)**: `예선진출용 자료모음/(붙임) 2026년 제8회 K-디지털 트레이닝 해커톤 개최 안내.pdf`
- **현재 동작하는 코드**: `바이브코딩/moveguard_mvp.html` (최신, 실제 실행됨), `바이브코딩/moveguard_prototype.html` (구버전 참고용)

## 팀 역할분담 (기획서 기준, 임의로 바꾸지 말 것)

- **김혜성** — 팀장/기획: 방향성 관리, 정책근거 조사, 신청서·기획서 작성, 멘토링 반영조율, 발표
- **신다빈** — 백엔드: RULA/REBA 모델 구현, MediaPipe 연동, FastAPI 서버, Firebase 연동, 법정서식 자동출력 로직
- **신운서** — 프론트엔드: 촬영 웹앱 UI, 관리자 대시보드, Figma 프로토타입, 위험도 신호등 시각화, 기술시연

새 작업을 나눌 때 이 담당 영역을 기준으로 제안한다.

## 이미 확정된 기술적 약속 (기획서에 명시됨 — 바꾸려면 기획서도 같이 고쳐야 함)

- 백엔드: **FastAPI + MediaPipe Pose Landmarker**, 채점은 **Python 룰베이스 엔진**
- 저장소: **Firebase (Firestore=이력, Storage=법정서식·사진)**
- 프론트: 기획서 원문은 **React**로 되어 있으나, 실제로는 바닐라 JS로 이미 완성·검증됨 — 이 차이는 팀이 의도적으로 결정한 사안이니, 어느 쪽으로 갈지는 팀 결정을 따르고 임의로 바꾸지 않는다.
- 하중 입력: **3단계 체크(가벼움/보통/무거움)** — 지금 mvp.html은 숫자(kg) 입력으로 되어 있어 기획서와 다름, 맞출지 여부 확인 필요
- 저신뢰 프레임: 조도 자동측정 대신 **관절 인식 신뢰도가 기준치 이하인 프레임은 일괄 제외하고 재촬영 안내** — 아직 미구현
- 개인정보: 원본 영상은 분석 후 **즉시 삭제**, 제출용 대표 사진 1장만 보관, 서버엔 관절좌표·위험도 결과만 저장
- 본선 시연: **사전 촬영해 둔 팀원 재연 영상을 재생하며 분석 시연** (시뮬레이션임을 발표 시 고지) — 현장 라이브 촬영이 필수는 아님
- 일치도 검증 목표: **KOSHA 매뉴얼 수기채점 대비 60% 이상(최소) / 70% 이상(목표)**, 테스트 영상 10~15건, 근골격계부담작업 2호 유형(목·어깨·팔꿈치·손목 반복동작), 측면 촬영 좌우 3사이클 이상

## 개발 확장 아키텍처 원칙 (RULA → REBA → OWAS 확장 대비)

REBA·OWAS는 기획서 로드맵상 **본선 이후(10월~) 사업 확장 단계**다. 지금 당장 만들 필요는 없지만, 나중에 만들 때 지금 짠 코드를 다시 파야 하는 상황을 막으려면 지금부터 이렇게 나눠 짠다:

- **공유 로직** (평가도구가 바뀌어도 그대로 재사용): 영상 업로드·프레임 샘플링, MediaPipe 포즈 추출, 관절 각도 계산 유틸(`angleBetween`, `vec` 등), 위저드 UI 뼈대, 법정서식 렌더링 틀
- **도구별 교체 조각**: RULA/REBA/OWAS 각자의 채점표·기준·Group 구성 — 이것만 새 모듈로 추가

버그를 하나 고칠 때, 그게 "공유 로직"에 있으면 나중에 REBA/OWAS에도 자동으로 적용된다. "도구별 조각"에 있으면 그 도구에만 적용된다 — 이 둘을 헷갈리지 않는 게 핵심.

## 개발 워크플로 (새 기능을 만들 때마다 이 순서)

1. **스펙 확인** — 0단계 문서에서 관련 내용부터 찾는다. 없으면 추측하지 말고 사용자에게 확인한다.
2. **실데이터로 먼저 검증** — 가능하면 코드를 짜기 전에, 짠 뒤에는 반드시, 실제 데이터(팀 자체 영상, 라벨링 데이터셋 등)로 돌려서 숫자로 확인한다. "될 것 같다"가 아니라 "이 정도 정확도가 나온다"를 보여준다.
3. **브라우저 실측 테스트** — 로컬 http 서버(`.claude/launch.json` 활용) 띄우고 실제로 눌러보고 확인한다. GitHub 코드뷰나 file:// 정적 스냅샷으로는 JS가 실행되지 않으니 이걸로 확인했다고 착각하지 않는다.
4. **배포 확인** — GitHub Pages(`https://hskim1771.github.io/MoveGuard/`)에 반영되는지 확인.

## 알아두면 시간 아끼는 것들 (겪었던 문제들)

- **GitHub 웹/앱은 `.html` 안의 JS를 실행하지 않는다.** 코드만 보여준다. 실제 동작 확인은 로컬 다운로드 후 열거나 GitHub Pages 주소로.
- **`<input capture>` 속성은 모바일 전용이다.** 데스크톱에서 안 보이는 게 정상.
- 이 저장소는 이미 GitHub Pages가 `main` 브랜치 루트로 켜져 있다 (재설정 불필요).
- MediaPipe 관련 배포(Render 등)는 의존성이 무거워서 무료tier 빌드/타임아웃 문제가 잘 남 — 항상 가장 먼저, 빈 뼈대로 조기 테스트할 것.
- 폴더명이 한글(`바이브코딩` 등)이라 일부 셸 명령에서 인코딩이 깨질 수 있다 — 문제 생기면 `find`로 경로를 다시 확인.
- Python으로 MediaPipe 쓸 때 최신 Python 버전 호환 여부를 먼저 확인 (venv 새로 만들어서 `pip install mediapipe` 테스트).

## 본선 규정 요약 (다시 찾아보지 않도록)

- 본선 1일차: 특정 장소·일정 시간 내 오프라인 멘토링 + **프로토타입 완성 및 제출**
- 본선 2일차: 팀별 시연·발표, 심사단 질의응답, 현장 심사
- 사전 준비 금지 규정 없음 — "구현가능성"이 정식 배점 항목이라 사전 검증은 오히려 유리
- 전체 팀원 필수 참석, 무단 불참 시 중도탈락 가능
- 심사 기준(예선): 참신성 30 / 구현가능성 30 / 현장실효성 30 / 보안성 10
